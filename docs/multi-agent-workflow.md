# LogiPlan 多 Agent 自动协同工作流

版本：V1.0  
日期：2026-08-21

## 1. 目标与原则

本工作流用于在 LogiPlan 中自动协调主 Agent 与子 Agent，同时控制 Token 消耗、上下文污染、并发写入冲突和高风险变更。

核心原则：

1. 复杂任务条件触发多 Agent，简单任务保持单 Agent。
2. 并行读取、单点写入；任何时刻最多只有一个源码写入者。
3. 同一工作流的实现与首次测试由同一个 `slice_owner` 连续完成，减少重复理解。
4. 高风险任务使用独立审查，但审查 Agent 不实施修复。
5. 交接使用结构化短摘要，不转发完整对话、长代码或原始日志。
6. 先查仓库和权威文档，只有命中暂停条件时才向用户提问。

## 2. 角色与资源配置

### 2.1 主 Agent

主 Agent负责初筛、最终分级、选择模型、编排顺序、压缩交接、处理审批、汇总结果和决定是否完成。主 Agent不把协调责任下放给子 Agent。

### 2.2 `context_scout`

- 模型：`gpt-5.6-luna`
- 推理强度：`medium`
- 沙箱：`read-only`
- 职责：以最小读取范围确认影响、冻结规则、验收条件、写入建议范围和 L2 信号。
- 限制：不修改文件，不给出超出证据的实现承诺。

### 2.3 `slice_owner`

- 沙箱：`workspace-write`
- L1：创建时显式使用 `gpt-5.6-terra` / `medium`
- L2：创建时显式使用 `gpt-5.6-sol` / `high`
- 职责：作为唯一写入者完成一个纵向工作流的影响确认、实现、测试和必要修复。
- 配置约束：角色文件不设置 `model` 或 `model_reasoning_effort`；每次创建时必须显式提供，禁止隐式继承。

### 2.4 `independent_auditor`

- 模型：`gpt-5.6-sol`
- 推理强度：`high`
- 沙箱：`workspace-write`
- 职责：独立检查实现和验收条件，运行必要验证。
- 限制：写权限只用于测试、构建和临时产物，禁止修改源码、测试、文档或配置。

### 2.5 并发

子 Agent 并发上限为 3，不包含主 Agent。只读探索可以并行；`slice_owner`、审查和返工按工作流顺序执行。即使存在多个空闲名额，也不得并发启动两个源码写入者。

## 3. 任务分级

### 3.1 初筛顺序

1. 主 Agent根据用户请求和一次最小只读检查判断任务是否明显属于 L0。
2. 明显 L0 由主 Agent直接处理，不创建子 Agent。
3. 不能明确判定为 L0 时，创建 `context_scout`。
4. 主 Agent根据最小交接包确定 L1 或 L2，并显式选择 `slice_owner` 的模型和推理强度。

### 3.2 分级定义

| 级别 | 适用范围 | Agent 配置 |
|---|---|---|
| L0 | 单文件小改、文案、明确测试修正，且无关键闸门影响 | 主 Agent直接处理，不创建子 Agent |
| L1 | 边界明确，需要探索和实现，但不触及任何 L2 条件 | `context_scout`：`gpt-5.6-luna/medium`；`slice_owner`：`gpt-5.6-terra/medium` |
| L2 | 冻结契约、精确计算、数据库、权限安全、日志、发布、公共接口、阶段闸门，或跨两个以上正式包 | `context_scout`：`gpt-5.6-luna/medium`；`slice_owner`：`gpt-5.6-sol/high`；完成后 `independent_auditor`：`gpt-5.6-sol/high` |

### 3.3 风险取高

- 任一 L2 条件成立，整个工作流按 L2。
- 无法确认是否触及冻结契约、精确计算、公共接口或其他 L2 条件时，主 Agent先做定向只读核查；仍无法排除则按 L2。
- L1 进行中发现 L2 信号时，原 `slice_owner` 停止继续写入并提交升级交接包。主 Agent创建新的 L2 `slice_owner` 接管；已有非破坏性改动保留并纳入审查。

## 4. 工作流边界与顺序

### 4.1 切片标准

按“共享页面目标、共享上下文、可独立验收”划分工作流，不按单个文件、单个查询类型或技术目录拆分。业务目标或主要页面改变时创建新的 `slice_owner` 会话；同一目标内的修复和测试继续使用原会话。

当前正式实现准备阶段的两个工作流为：

1. 驾驶舱工作流：`MONTHLY_COST_TREND`、`TOP_ADVERSE_ANOMALIES`、`FIXED_COST_BREAKDOWN`。
2. 归因页诊断工作流：`DIAGNOSTIC_METRICS`。

### 4.2 L1 流程

`主 Agent初筛 → context_scout → 主 Agent定为 L1 → slice_owner 实现并自测 → 主 Agent验收`

若过程中出现 L2 信号，立即执行升级规则。

### 4.3 L2 流程

`主 Agent初筛 → context_scout → 主 Agent定为 L2 → slice_owner 实现并自测 → independent_auditor 审查 → 主 Agent验收`

## 5. 最小交接包

`context_scout` 到主 Agent、主 Agent到 `slice_owner` 的交接字段：

- `objective`：工作流目标
- `level` 或 `suggested_level`：分级及证据
- `acceptance`：可验证的完成条件
- `relevant_files`：相关文件和关键符号
- `invariants`：冻结决策、契约和数值关系
- `write_scope`：允许修改与禁止修改的范围，包括已有未提交文件
- `verification`：必须执行的验证
- `risks`：未解决问题、假设和升级条件

`slice_owner` 到 `independent_auditor` 额外包含：

- `changed_files`
- `implementation_summary`
- `invariants_checked`
- `tests_run`
- `tests_not_run`
- `remaining_risks`
- `git_status_delta`

交接包只提供路径、符号、决策编号、命令和结果摘要。原始日志留在对应 Agent 会话，需要时定向读取。

## 6. 强制独立审查

出现以下任一条件，完成自测后必须启动 `independent_auditor`：

- 修改冻结业务口径、查询契约、证据结构或高精度计算
- 修改数据库迁移、权限、安全、日志或发布流程
- 修改公共接口或跨越两个以上正式包
- 进入阶段闸门、合并或公开部署前
- 实现过程中出现数据勾稽失败或测试不稳定

纯样式、小范围文案和测试内部整理等低风险修改不强制独立审查。

## 7. 返工与停止

一次返工轮次定义为：

`independent_auditor 发现问题 → 原 slice_owner 修复并自测 → 原 independent_auditor 定向复查`

审查问题必须返回原 `slice_owner`，复查必须返回原 `independent_auditor`，以复用两侧上下文。第二轮复查仍未通过时，无论问题是否纯技术，立即停止相关 Agent，并向用户报告：

- 仍未通过的验收项
- 两轮已经尝试的修复
- 当前代码和测试状态
- 继续处理所需的一个明确决策问题及推荐答案

## 8. 分级验证矩阵

### L0

运行与改动直接相关的最小测试或静态检查。

### L1

- 定向单元或集成测试
- 受影响 workspace 的类型检查
- 适用的 lint 和格式检查

### L2

- `pnpm test`
- `pnpm typecheck`
- `pnpm lint`
- `pnpm format:check`
- `pnpm build`
- 数据库相关变更追加迁移、发布、权限、核心查询和查询计划验证
- 页面相关变更追加对应浏览器验收

### 阶段闸门、合并或部署前

在 L2 基础上追加覆盖率、完整 Playwright，以及路线图规定的性能和可访问性检查。

因环境、权限或依赖无法执行的检查必须标记为“未执行”并说明原因，不得表述为通过。

## 9. Git 与工作区规则

- 每个写入和审查任务开始前记录 Git 状态，区分用户原有改动、任务改动和测试产物。
- 用户已有改动不得覆盖、回滚、清理、格式化或夹带到任务范围。
- 子 Agent不得创建分支、提交、暂存、变基、合并、推送或改写历史。
- 禁止使用 `git reset`、`git restore`、`git checkout --` 等方式清理工作区。
- 只有主 Agent在用户明确要求后才能执行提交、分支或远程 Git 操作。
- 默认不为子 Agent创建独立 worktree。

## 10. 自动操作与审批边界

可自动执行：

- 只读检索、构建、测试、类型检查和静态检查
- 使用现有锁文件安装冻结依赖，但不得修改依赖清单或锁文件
- 启停项目自带的本地 Docker Compose
- 在明确隔离的本地或 CI 临时 PostgreSQL 中执行迁移、演示数据发布和验证
- 生成可删除的测试、覆盖率和构建产物

必须先获得用户授权：

- 新增、删除或升级依赖
- 使用真实密钥、付费 API 或外部账户
- 修改 Neon、Vercel、GitHub 等远程环境
- 部署、公开发布、创建远程数据库分支或写入共享数据库
- 发送外部消息、创建 PR、提交远程任务或触发具有外部影响的工作流
- 删除数据、清理非临时资源或执行不可逆操作

无法确认数据库或服务是否为本地隔离环境时，默认按远程资源处理并停止请求授权。

## 11. 暂停并向用户提问的条件

仅在以下情况暂停：

- 存在无法从仓库、冻结决策或权威文档推导的产品或业务取舍
- 需要外部操作、远程写入、依赖变更或破坏性操作授权
- 必须修改用户已有未提交内容且无法安全隔离
- 两轮修复—复查后仍未通过
- 发现可能导致数据泄露、权限扩大或不可逆数据损坏的风险
- 用户要求相互冲突，且不同解释会产生实质不同结果

其他技术问题由主 Agent先检索知识库和代码，采用影响最小的合理假设，记录后继续执行。

## 12. 运行记录与配置验收

- 不提交逐次 Agent 对话、原始日志、临时任务文件或常规 worklog。
- 只在形成长期有效结论时更新正式项目文档。
- 工作跨会话中断且无法完成时，可以输出精简继续工作摘要，但默认不写入仓库。
- 配置落地后先检查 TOML 语法、必填字段、模型继承边界、权限、并发和 Git 差异。
- 仓库级配置应在新的 Codex 任务中做只读演练：只执行分级、`context_scout` 和最小交接，不修改代码。演练通过后再开始正式实现。
