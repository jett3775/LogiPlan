## 2. 本窗口已完成的工作（不需重做）

### 2.1 `pg` 单连接并发弃用告警的完整修复（跨两个提交）

**问题**：`pg@8.23.0` 对**同一个 `Client`** 并发提交 `query()` 会触发 `DeprecationWarning`
（`pg@9` 将移除该行为）。该告警在 Web V1.1 请求路径与发布物化路径上真实出现
（首次记录为 2026-09-27 E1 激活日志）。

**提交**：`7e089efb`（`fix(db): 串行化单连接查询以消除 pg 并发弃用告警`）、`381cd18f`（补记 CI 证据）。

**关键设计决策**：只在**两个单连接判定点**注入串行化——`runDeterministicQuery` 的 `pool.connect()`
之后、`materializeEvidenceSnapshots` 函数首行。**V1.0 纯 Pool 分支与三处 `Promise.all` 刻意保持不变**，
因为 `pg-pool` 的 `Pool.query` 每次取独占 client 后立即 release，结构上不可能触发该通知；
改动它们既无收益又会摧毁池级并发，也会破坏 `verify-query-plans.ts` 靠 `Proxy` 拦截
`pool.query` 采集查询计划的机制。

**证据链**：

- 三段反向对照（真实 `postgres:18.4`，独立进程）：同一 `Client` 并发 → **告警出现**（证明探针有效）；
  promise 链 → 零告警；真实 `Pool` `max:2` 并发 6 条 → 零告警。
- 完整 `pnpm verify:gate1:isolated` 以 `NODE_OPTIONS=--trace-deprecation` 跑完，全程零告警，
  含历史上告警真实出现的激活物化步骤。
- CI run `37167407079`、`37251054937` 等，全绿。

**文档**：`docs/pg-concurrency-deprecation.md` §8（落地记录）、`docs/development-roadmap.md` §0
遗留项 5 的 2026-10-02 dated 注记（**修正了一个被证伪的旧归因**：原写「三处并发 `pool.query()`
配合 `max: 2`」，实际不成立）。

### 2.2 `QueryTarget` 类型显式化与 nominal brand

**提交**：`54dce871`（`refactor(db)`）、`6a9f72d8`（文档回填）、`97c684f5`（端到端证据）。

把 `serializeQueries` 的逻辑并入唯一工厂 `createQueryTarget(source, concurrency)`，
并给 `QueryTarget` 加**模块私有 `unique symbol` nominal brand**。

**为什么加 brand**：审查发现 `QueryTarget` 是纯结构类型时，手写字面量
`{ db: client, concurrency: "single" }` 能**完全绕开工厂且 `tsc` 零报错**，
得到一个「自称已串行化但实际未串行化」的目标。这与本项目此前纠正 `pg` 归因时
用的是同一标准——**不让注释里的话被证伪，而是让它成真**。

**缺口的真实状态（勿夸大）**：

- **已闭合**：裸 `Client`、`Pick<Client,"query">`、包装对象、`{}`、手写 `{ db, concurrency }`
  在编译期全被拒绝，**无法伪造**并发目标。
- **未闭合**：类型只证明「对象出自工厂」，**不证明 `concurrency` 实参传对**。
  对单连接误传 `"pool"` 类型仍成立但不串行化，这一层由既有行为测试（单连接在飞计数探测）兜底。

## 6. 已记录的环境限制（不是缺陷，不得「修复」）

1. **`Firefox 核心冒烟` 在 macOS 27.0 预发布版上无法运行**。签名：`0ms` 失败、用例体未执行、
   零断言失败。成因是内容进程沙箱扩展签发被拒（`sandbox_extension_issue_file_to_process …
Operation not permitted`）。CI 对照探针（run `36739876157`，macOS **26.6.2** runner）证明
   同一构建、同一 ad-hoc 签名的 Firefox **正常启动** ⇒ 变量是**操作系统版本**，
   非仓库或构建缺陷，**升级依赖无依据**。收口口径（用户已批准）：macOS 本机该腿记为
   **本地环境限制**，稳定性权威证据**仍为 CI**（ubuntu 的 `gate1` job 真跑 Firefox 腿）；
   **与 D-188 的 Windows 限制平台不同、不得合并**。复核触发条件：macOS 27 转正式版，
   或上游 Playwright / Firefox 构建更新。详见 `docs/current-plan.md` 与
   `docs/development-roadmap.md` §0 的 2026-09-30 注记。
2. **不得用浏览器启动参数类开关绕过**（如关闭内容进程沙箱）——属明确不做项，需单独批准。
3. **`registry-1.docker.io` 从本机不可达（2026-10-05 实测）**。Docker daemon 正常（29.8.1），
   `api.github.com`、`registry.npmjs.org`、`ghcr.io` 均 TLS 正常，故**不是 Docker 未启动、也不是
   全网问题，而是 Docker Hub 单独不通**：TCP 443 不可连，TLS 握手被重置
   （`docker pull postgres:18.4` 约 60 秒后 `context deadline exceeded` 或 `EOF`）。
   **后果**：本机镜像库存只有 `postgres:18.6`，而 `compose.yaml:5` 与 `verify:gate1:isolated`
   的数据库集成腿 1 都钉 `postgres:18.4`，因此 **`pnpm db:up`、`pnpm verify:gate1:isolated`、
   任何需真实数据库的 Playwright 用例在本机一律无法完成**（`scripts/neon-baseline.test.mjs:143`
   的 `runDocker` 有 `timeout: 60_000`，拉镜像超时会被误判成用例失败——**这个签名要认得**）。
   **收口口径**（D-188）：Gate 1 的权威证据取 CI ubuntu；本机此限制与 CI 结果**分别记录、不得合并**。
   **恢复方式（需用户决定，见 `docs/current-plan.md` §6）**：开代理/VPN 后按官方源拉取；或用户告知
   可访问的镜像源（但官方源不通 ⇒ 无法取官方 digest 比对，只能信任该源）。
   **明确禁止**：给本机 18.6 打 `postgres:18.4` 标签冒充——那是把欺骗固化进验证记录。

## 7. 本窗口的关键事实与陷阱（供后续会话避免重复试错）

1. **闸门二 AI 层不得走 `POST /api/v1/query`**。`MANAGEMENT_ANALYSIS` 当前在
   `packages/db/src/query-service.ts:590` 是**被拒绝**的 question_type
   （「管理分析必须消费确定性结果集合，不能直接查询事实」）。AI 层必须是独立路由
   在服务端内部调用查询服务函数。
2. **两套证据 ID 体系零交集**。真实 `evidence_id` 形如 `E01-country`、
   `ATTRIBUTION_BRIDGE:<factor>`、`DIAGNOSTIC_METRICS:<metric>:<slot>`、
   `ATTRIBUTION_DRILLDOWN:<row_id>`、`E08-<fulfillment_center_id>`；
   评估集 `evidence` 字段形如 `country_summary|ACTUAL|2026-08|GB`，
   那是**溯源标签**，**不是** `EvidenceObject.evidence_id`。
   详见 `docs/gate2-design.md` §5.1 与 §4.3 的 dated 注记。
3. **证据白名单是范围锚定的，不是全局扁平集合**。`EVIDENCE_LOOKUP` 对 `canonicalScope`
   不一致直接返回 `INVALID_FILTER`（`query-service.ts:2080`）。
   在英国归因范围下，`E08-*`、`E04-total`、`FIXED_COST_BREAKDOWN:*`、
   `MONTHLY_COST_TREND:*`、`TOP_ADVERSE_ANOMALIES:*` **均不可解析**。
4. **`pnpm-lock.yaml` 在执行闭包内**，任何依赖或 workspace 包变更都会使工具 SHA 失效。
   这是预期结果，**不要试图修复或改文档**。
5. **多平台矩阵不参与 Gate 1 稳定性判定**（那是 ubuntu `gate1` job 的职责，D-188），
   但它**不是冗余**——Windows 独有的路径分隔符缺陷只能由它发现（见 §2.3 第 3 点）。

6. **⚠️ 陈旧的 `apps/web/tsconfig.tsbuildinfo` 会让 `pnpm typecheck` 假绿**。`apps/web/tsconfig.json`
   有 `"incremental": true`；`pnpm typecheck` 跑 `tsc -p` 复用该缓存，而 `next build` 用
   `cacheDir/.tsbuildinfo` 这一**另一条路径**。结果是**一条真实的类型红可以只被 typecheck 漏掉、
   被 build 抓到**——切片 1b 的 P0 就是这样被掩盖的，一度被误报成「typecheck 5 workspace Done」。
   **凡验证类型或构建，必须先 `rm -f apps/web/tsconfig.tsbuildinfo` 并考虑 `rm -rf apps/web/.next`**，
   否则验证结论不可信。
7. **固定示例的 `evidence_snapshot_id: "SNAPSHOT_GB_2026_08_V1"` 是编造占位值**，硬编码在
   `packages/ai/src/fixed-example/fixed-example.ts` 约 `:213`，且它**恰好能通过**
   `evidenceSnapshotIdSchema`，所以失败是**静默**的。1b 已用服务端真实 `ES-<uuid>` 替换，
   但**1a 层面没有让这个取值被 schema 显式拒绝**——后续切片如有机会改 `packages/ai`，应把它改为
   显式标记的非法值，避免同类静默失败。
8. **子 Agent 的「过度保守」需要主 Agent 复核**。切片 1a 中子 Agent 因担心违反
   AC1.13 而不敢改 `snapshot-store.test.ts` 里的旧 ID 夹具，但该文件是本切片新建的
   未跟踪文件（`git ls-files` 返回 0 行），编辑完全在范围内。这类残留若无人纠正
   会变成永久技术债。
